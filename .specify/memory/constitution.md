# 블로그 프로젝트 Constitution

> 이 헌법은 `docs/상세/`(요구사항)과 `docs/가이드/`(기술 설명)에 이미 적힌 원칙을 모아,
> Spec Kit의 모든 단계(specify → plan → tasks → implement)가 따를 규칙으로 정리한 것이다.

## Core Principles

### I. 요구사항 문서가 원천이다

- 기능은 `docs/상세/`의 요구사항 ID(`CF-xx`, `BM-xx`, `NF-xx`)와 연결되어야 한다(MUST).
  spec, plan, tasks, 코드 리뷰에서 근거 ID를 적는다.
- 요구사항은 "무엇을 할 수 있어야 하는가"만 적는다. 어떤 기술로 만들지는 `구현 방식`과 plan에만 적는다.
- 요구사항이 바뀌면 문서를 먼저 고치고, 그다음 `구현 방식`과 코드를 점검한다. 코드가 문서보다 앞서지 않는다.
- 결정 상태는 **확정 / 가안 / 미정**으로 표시하고, `확인 필요` 표시가 남은 항목은 합의된 것으로 보지 않는다.

**이유**: 팀 합의 문서(`요구사항-공통.md`)와 개인 상세 문서가 함께 있어, 근거가 흩어지면 무엇이 맞는지 알 수 없다.

### II. 규칙과 권한은 서버가 지킨다 (NON-NEGOTIABLE)

- 글자 수, 형식, 필수 여부, 수정·삭제 권한, 비공개 글 노출 여부는 **서버에서** 검사한다(MUST).
  화면의 검사와 버튼 숨김은 안내일 뿐이다. (NF-02)
- 비밀번호는 되돌릴 수 없는 해시로만 저장하고, 원문을 DB·로그·오류 메시지에 남기지 않는다. (NF-01)
- 오류 메시지와 응답(문구, 제한 동작 포함)은 계정이 있는지, 비공개 글이 있는지, 내부 구조가 어떤지 드러내지 않는다. (NF-06, CF-02-3, CF-09-4, CF-25-3)
- 인증번호 같은 값은 추측할 수 없고, 한 번만 쓰이며, 시간이 지나면 사라진다. (NF-05)
- 본문·댓글의 스크립트는 실행되지 않고, 입력값으로 DB를 조작할 수 없다. (NF-07)
- 로그인 정보는 스크립트가 읽을 수 없고, 다른 사이트의 요청으로 동작이 실행되지 않으며, 로그인마다 새로 발급된다. (NF-10~12)

**이유**: 화면을 건너뛴 요청은 언제든 올 수 있고, 계정 존재 여부 같은 작은 노출도 공격의 시작이 된다.

### III. 단순함을 고른다

- **단일 서버**로 만들고 안에서 기능별로 나눈다. 서비스를 쪼개는 구조(MSA)는 쓰지 않는다(MUST).
- 모듈은 정해진 방향으로만 부르고, 서로 부르는 순환을 만들지 않는다.
- 요구사항에 "이번 범위에서는 만들지 않는다"로 적힌 기능(관리자 화면, 소셜 로그인, 댓글 수정, 썸네일,
  프로필 사진, 알림 목록·메일·푸시, 유입 경로 통계 등)은 만들지 않는다.
- 더 복잡한 선택지(토큰 인증, 여러 블로그, 형태소 검색 등)는 요구사항이 바뀌었을 때만 다시 검토한다.

**이유**: 2주 동안 혼자 구현하는 규모이며, 단순한 구조가 요구사항(즉시 로그아웃, 다른 기기 끊기)을 가장 쉽게 지킨다.

### IV. 숫자는 한곳에서 바꾼다

- 글자 수, 개수, 용량, 시간 같은 기본값은 각 상세 문서의 `기본값` 표와 같은 값을 쓰고,
  코드에서는 **설정 한곳**에서 읽는다(MUST). 코드 곳곳에 숫자를 박지 않는다. (NF-08)
- 기본값을 바꾸면 문서의 `기본값` 표를 같이 고친다.

**이유**: 기본값은 아직 바뀔 수 있는 값이라, 흩어져 있으면 문서와 동작이 어긋난다.

### V. 바꿔 끼울 수 있게 외부에 기댄다

- 외부 서버 프로그램(DB, Redis, 이미지 저장소, 메일)은 접속 정보를 설정으로 분리하고, 코드에 박지 않는다.
- 유지보수가 끝난 도구(MinIO 공개판)나 아직 정하지 않은 도구(SMTP 계정, 배포 환경)는
  인터페이스 하나 뒤에 두어 다른 구현으로 바꿔 끼울 수 있게 한다(MUST).
- 비밀번호·키 같은 비밀 값은 저장소(Git)에 올리지 않는다.
- 외부 저장소·메일 서버는 우리 서버만 접속하고, 바깥에 포트를 열지 않는다.

**이유**: 배포 환경과 일부 도구가 미정이라, 나중에 바뀌어도 요구사항과 대부분의 코드는 그대로 두기 위해서다.

### VI. 누구나 읽을 수 있게 쓴다

- 문서는 한국어로, 개발을 처음 하는 팀원도 읽을 수 있게 쓴다. 낯선 개념은 `쉬운 설명`을 먼저 둔다.
- 화면 문구는 "~합니다 / ~해 주세요" 말투로 통일하고, 각 문서의 `안내 문구` 표를 따른다.
- 휴대폰 화면(폭 360px 이상)에서도 가로로 밀지 않고 읽고 쓸 수 있어야 한다. (NF-03)

**이유**: 팀원 모두가 문서를 읽고 같은 그림을 그려야 합의가 빠르다.

## 기술·범위 제약

| 영역 | 내용 | 상태 |
|---|---|---|
| 서버 구조 | 단일 서버, 기능별 모듈 | 확정 |
| 인증 | 서버 세션(쿠키). 세션은 DB에 저장, 마지막 사용 후 7일 유지 | 확정 |
| 임시 저장 | 이메일 인증번호 등 만료가 필요한 값은 Redis | 확정 |
| 서버 / 화면 / DB | Spring Boot + Spring Security / React(Vite) / PostgreSQL, REST(JSON) | 가안 |
| 이미지 저장 | MinIO(S3 방식) 또는 서버 디스크, 인터페이스로 교체 가능 | 가안 |
| 개발 환경 | DB·Redis·이미지 저장소는 Docker Compose로 로컬 실행 | 가안 |
| 메일 발송 / 배포 환경 | SMTP 계정과 배포 위치 | 미정 |
| 성능 | 글 목록과 글 상세는 2초 안에 보여 준다 (NF-09) | 확정 |

외부 서비스는 쓰지 않는 것이 원칙이며, 메일 발송(SMTP)만 예외로 둔다.

## 개발 흐름과 품질 기준

- 기능은 Spec Kit 순서를 따른다: `/speckit-specify` → (필요하면 `/speckit-clarify`) → `/speckit-plan`
  → `/speckit-tasks` → `/speckit-implement`.
- plan은 이 헌법의 원칙을 하나씩 확인하는 "Constitution Check"를 통과해야 한다.
  원칙을 어기는 설계는 이유와 더 단순한 대안을 버린 까닭을 plan에 적어야 한다.
- 권한 검사, 비공개 글 노출, 인증번호·로그인 잠금, 계정 존재 비노출 규칙은 자동 테스트로 확인해야 한다(SHOULD).
- 데이터 구조(ERD)는 요구사항 ID를 근거로 연결해서 만든다.

## Governance

- 이 헌법은 `docs/`의 다른 관례보다 우선한다. 충돌하면 헌법을 기준으로 문서를 고치거나, 헌법을 개정한다.
- 개정은 바뀐 내용, 이유, 영향 받는 문서를 Sync Impact Report에 적고 버전을 올린다.
  - MAJOR: 원칙 삭제나 뜻을 뒤집는 변경
  - MINOR: 원칙·섹션 추가, 미정 항목의 확정
  - PATCH: 문구 다듬기, 오타
- spec, plan, 코드 리뷰는 원칙 II(서버 검사)와 III(단순함) 위반 여부를 매번 확인한다.
